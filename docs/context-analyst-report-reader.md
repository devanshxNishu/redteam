# Historical context report data

`readContextAnalystReport(store, taskId, options?)` reads an existing normal context report. This internal helper does not run a model. It has no terminal, API or web route yet.

The reader requires a task-backed manifest, a supported terminal task and its ordered event history, an exact private `report.json`, and current brief, context source and processing rights. It reads the complete saved source, snapshot, processing, manifest and generation files. A candidate-bearing report must match the separate checked historical candidate reader and the completed task output. A factual failed report has no candidate. Missing reports, unpublished candidates and seals are unavailable; the reader does not promote them.

The supported record is schema 2.0, kind `unreviewed_context_analyst_run`, policy `brief-context-analyst-report-v1`. It preserves the original compact bytes and the historical boundaries, including `historicalFinalReportReading: not_implemented` and `cleanup: record_created_before_resource_closure`. Those fields describe the record written by the original coordinator. They do not confirm cleanup or disable this separate data inspection helper.

The reader checks recorded budget caps, invocation identities, amounts, states, overrun flags and pool sums. Recorded request flags must agree with task dispatch intents and supported reservation states. A sent request cannot become a released reservation in this record. Unknown costs remain held. Counting is not assumed free. All amounts use configured rates and local records; they are not provider invoices or independently authenticated receipts.

The reader does not open the current budget database. Later settlement can change that ledger without changing this historical snapshot. An absent current ledger is not created or treated as zero. Budget `asOf` is a local marker written before the original snapshot call; a concurrently recorded receipt can be later than this marker. The reader does not invent an upper receipt timestamp or settle, release or retry an invocation.

Options accept a native `AbortSignal` and an integer `timeoutMs` from 1 to 60000, with a 30000 ms default. The caller read window does not extend source or processing rights. A report can be read after its original task deadline only while current rights remain valid. Cancellation withholds delivery. Pending read-only work can finish without gaining task or publication authority.

Task reads use bounded direct read-only SQLite access and a read transaction. Main database and WAL identity, mode, size and timestamps must remain stable through that transaction and database closure. A concurrent local write is conservatively unavailable. They do not construct a TaskStore or BudgetLedger, repair schemas or permissions, or create missing files. Complete source and report checks repeat after asynchronous reads. The public return frame checks pinned file identity, private mode, link count, size and timestamps, the current task and current permissions after its last await. Any change is conservatively unavailable. These checks do not claim an atomic transaction across the filesystem, clock and databases. The trusted local operator, runtime, metadata, filesystem and backups remain boundaries.

The returned `checked_historical_context_report_data` is data only. It grants no execution, ownership, runtime observation or publication receipt. All analytical content remains unreviewed. This helper does not establish app correctness, broad global awareness, researched psychology, purchase demand, investment decisions, funding probabilities or commercial validation. Conservative recovery, discovery, terminal execution and semantic/usefulness evaluation remain separate work.

Verification uses authored fake HTTP and controlled fixture clocks, including deliberate timeout and expiry advances. These checks establish local record consistency and delivery guards. They do not establish native wall-time liveness during host suspension. Full product regressions and versioned package/install checks are recorded separately.

The record and event output limits do not independently bound whole-database scan work. The existing event table has no dedicated task index. A JavaScript timeout cannot preempt a synchronous SQLite operation while the event loop is blocked; current guards withhold late delivery when control returns. Hard native execution-time isolation remains separate production work.
